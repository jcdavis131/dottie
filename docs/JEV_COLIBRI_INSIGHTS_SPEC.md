# JEV_COLIBRI_INSIGHTS_SPEC — external research adoption, scoped and verified

Two outside projects were researched for transferable learnings and baked into
`packages/dottie-loop`, following the same status vocabulary as
[`docs/LONGCAT2_INSIGHTS_SPEC.md`](LONGCAT2_INSIGHTS_SPEC.md): **BUILD-NOW**
(implementable now, CPU-only, pytest-gated, no frozen path touched),
**SPECED-DEFERRED** (design recorded, blocked on something real), or a third
status this doc introduces, **DO-NOT-ADOPT** (considered and refused, with a
written reason, so the same idea does not get re-proposed without new
evidence).

## TL;DR

- **TypeSafe Jev** (a hosted, closed-weight "System One" decision model that
  answers a typed question with a choice and a probability; launched
  2026-09-15) contributes exactly one surviving rule: an external backend's
  probability must never be named or treated as one of the four things this
  codebase already calls `confidence`. That rule ships as
  `dottie_loop/backend_signal.py`.
- **JustVugg/colibri** (a pure-C inference engine whose own
  `c/experiment_manifest.py` mechanically enforces "re-derive the headline
  number, don't trust it") contributes a two-arm evidence record — every
  median and the changed configuration key are *computed*, never accepted as
  a caller's claim, and a comparison without a recorded, interleaved run
  order can never pass a gate. That ships as `dottie_loop/manifest.py`.
- Fourteen other Jev-derived learnings and twelve other colibri-derived
  learnings were generated by the same research pass and did **not**
  survive independent adversarial review (three lenses per learning: does
  the evidence actually say this; does it violate a Dottie invariant; does
  it duplicate something that already exists — kept only when at least two
  of three did not refute it). A further 14 (Jev) and 16 (colibri)
  candidates were declined by the distillation pass itself, before
  verification even ran. All of them are recorded below with the reason,
  so "we looked at this and said no" is as durable as "we looked at this
  and said yes."
- **No model is called anywhere in either new module.** Neither TypeSafe's
  API nor colibri's engine is installed, run, or depended on. This PR adds
  two small validators; it does not measure anything about Dottie itself.

## Context: what each project actually is

**TypeSafe Jev.** TypeSafe AI (co-founder Diogo Almeida) announced Jev,
its first "System One" model, on 2026-09-15: a hosted, closed-weight model
that takes a JSON `state` plus one or more typed `questions` (boolean,
pick-one, or an ordered score rubric) and returns a choice and a
probability, never free text. Its own SDK docs describe the returned
`confidence` as "derived from the shape of the distribution" with the
formula undisclosed, and TypeSafe's own SKILL.md says it "summarizes
distribution concentration, not overall workflow correctness or permission
to act." No public reliability curve exists for it; a community
reproductions tracker's own summary of independent testing is "confidence
does not reliably flag errors," and live integration traces (351 recorded
calls, vinilana/jev-eval-agent) show wrong-tool picks at 0.79–0.88
confidence. Community reproductions (openjev, pngwn/system-one) exist and
are themselves distribution-limited (384-token training windows, 16-option
caps). None of Jev's weights, training method ("RLCD" is TypeSafe's own,
undisclosed term — not the unrelated published RLCD alignment method,
arXiv:2307.12950), or infrastructure is available to run locally, and this
codebase's doctrine ("no model is called anywhere in this package") means
none of that changes even if it were.

**JustVugg/colibri.** colibri (github.com/JustVugg/colibri, Apache-2.0,
~35.8k stars) is a pure-C, zero-dependency inference engine that streams
744B–2.8T-parameter mixture-of-experts models across VRAM/RAM/NVMe on
consumer hardware. Its engineering is out of scope for a stdlib contracts
package with no model calls and no GPU on this box (measured 2026-08-01:
16.9 GB RAM against colibri's own 25 GB floor, 59 GB free disk against a
372 GB minimum model — see "Not adopted" below), but its **experiment
doctrine** is directly reusable: `c/experiment_manifest.py` mechanically
enforces a full 40-hex commit, at least three raw samples per arm, a
median re-derived from those samples (not a claimed one, checked within
1e-6), a changed-configuration key computed from a diff of the two arms
(not declared), and a passing named correctness check — enforced by five
unit tests colibri's own CI runs on three OSes. colibri's own experiment
logs document real measurement failure modes that motivate recording run
order: two identical runs on a quiet box differed by 38.8%; an unpaired
cap-size sweep disagreed about the *sign* of an effect that seven-of-eight
alternating pairs later resolved.

## What landed

### 1. `backend_signal.py` — an external backend's probability is never `confidence`

**Status: BUILD-NOW.**

- **Target files:** `packages/dottie-loop/dottie_loop/backend_signal.py`
  (new), `packages/dottie-loop/tests/test_backend_signal.py` (new, 10
  tests), `schema.py` (`backend-probability-1.0.0`), `components.py`,
  `README.md`, `__init__.py`.
- **Design:** `BackendProbability(value, backend, provenance)` is a frozen
  record: `value` must be a non-bool number in `[0, 1]`; `backend` and
  `provenance` must be named. `to_dict()` stamps the value under the key
  `backend_confidence` — never `confidence` — alongside `backend` and
  `provenance`, so it can never be silently confused with the four
  existing, unrelated meanings of `confidence` already in this codebase
  (`reward.form_preference_pair`'s margin, `memory.Fact`'s writer-asserted
  strength, `rlm`'s worker-reported number, and hand-typed figures in
  `docs/LESSONS.md`). `reject_confidence_aliasing(record)` raises
  `PolicyDeniedError` if a record carries `backend_confidence` next to any
  of `{confidence, score, prob, p}`. Nothing in this module compares
  `value` to a threshold, bands it, recomputes it, or feeds it to
  `evaluation.calibration` — doing any of those would require a measured
  reliability record this module does not have and does not fabricate.
- **Tests:** value bounds and bool rejection; backend/provenance
  non-empty; `to_dict()` names the field `backend_confidence` and never
  emits `confidence`; the value round-trips verbatim; the aliasing guard
  is a no-op without `backend_confidence` present, refuses every forbidden
  alias, and allows `backend_confidence` alone.
- **Reversal trigger:** none identified; this is a naming guard with no
  moving parts to be wrong about. It would be revisited only if this
  codebase adopts a real decision backend (see "Not adopted", J1/J13) and
  needs `BackendProbability` embedded in a larger record.

### 2. `manifest.py` — a two-arm comparison every number is re-derived from

**Status: BUILD-NOW** (narrower than the fully verified contract — see
"Fork taken" below).

- **Target files:** `packages/dottie-loop/dottie_loop/manifest.py` (new),
  `packages/dottie-loop/tests/test_manifest.py` (new, 17 tests),
  `packages/dottie-loop/dottie_loop/cli.py` (`research manifest --file`
  subcommand), `schema.py` (`experiment-manifest-1.0.0`), `components.py`,
  `README.md`, `__init__.py`.
- **Design:** `ExperimentArm(commit, config, raw_samples, quality_method,
  quality_passed, evidence_uri, evidence_sha256, dirty_tree=False)`
  validates a full 40-hex commit, at least `opt_lane.MIN_MEASURED` (3)
  finite positive raw samples, a non-empty evidence URI and a 64-hex
  evidence digest, and refuses a dirty-tree measurement outright. `.median`
  and `.n` are computed *properties* — there is no field a caller can set
  to claim a false one. `ExperimentManifest(hypothesis, baseline, trial,
  lower_is_better=True, run_order=())` refuses a baseline arm that failed
  its own correctness check ("a broken baseline measures nothing") but
  **admits** a failed trial arm (negative results are first-class) and
  marks it `gate_eligible=False`. `.changed_variables` is computed from a
  diff of the two arms' `config` dicts — there is no declared value to
  disagree with the data, because none is accepted. `run_order`, when
  given, must name each arm exactly as many times as it has samples;
  `order_kind()` classifies it `interleaved` (ABAB/ABBA, no run of the
  same arm longer than 2), `blocked` (one arm run to completion before the
  other), or `not_recorded`. `.gate_eligible` is `True` only when both
  arms passed correctness *and* the order was interleaved — a blocked or
  unrecorded order is filed but can never gate, whatever the medians say.
  `.pair_wins` counts wins/losses/ties from the two arms' same-length,
  interleaved sample lists and is `None` — never a fabricated zero — when
  pairing is not possible. `to_dict()` stamps `schema` and a
  `content_sha256` over the full evidentiary body via `hashing.digest`. A
  new CLI subcommand, `python -m dottie_loop research manifest --file
  m.json`, exercises it end to end (`EXIT_OK` / `EXIT_INVALID`, matching
  every other `research` subcommand's contract).
- **Tests:** commit/hex/dirty-tree validation; sample-count and
  finite-positive validation; evidence-hash and quality-method validation;
  median/n are computed, never stored; a failed baseline raises, a failed
  trial is admitted but gate-ineligible; `changed_variables` is computed
  including the "key present on only one side" case; a caller cannot
  inject a false median (no such constructor parameter exists);
  `order_kind` classifies interleaved/blocked/not-recorded correctly;
  `run_order` length/name mismatches are refused; a blocked or
  not-recorded order is filed but never gate-eligible; a correctly
  interleaved, correctness-passing pair is gate-eligible;
  `higher_is_better`/`lower_is_better` flips direction and pair wins
  correctly; version/hypothesis validation; `to_dict()` is content-hashed
  and schema-stamped; the CLI round-trips a good record to `EXIT_OK` and a
  bad one to `EXIT_INVALID`.
- **Reversal trigger:** none for what shipped. The deferred pieces below
  are each gated on something concrete (a real comparative benchmark to
  file, or a `factory`/`mlops.py` integration point).

## Fork taken — where the shipped contract is narrower than the verified one

The adversarial-review pass that ran ahead of this PR wrote each surviving
learning as a large, fully worked contract (field-by-field, with its own
test list). Two of the four survivors depended on machinery that its own
sibling learnings did **not** survive, and the colibri contract's full
form reaches into four files outside `packages/dottie-loop` this PR does
not touch. Rather than build the maximal version, this PR ships the
smaller, self-contained core of each and defers the rest:

- **J6's contract assumed a `DecisionRecord` type from J1.** J1 (a
  closed-set decision record with a request-relative distribution check)
  was refused 0-of-3 by adversarial review — the same review that kept J6
  itself flagged, on its one dissenting (redundancy) vote, that J6 "only
  makes sense as a subsection of J1." Building a `DecisionRecord` this
  codebase has no consumer for, just to give a naming guard somewhere to
  live, would be exactly the kind of speculative surface this repository's
  own doctrine (`gate_audit.py`: "a gate whose verdict nothing consumes")
  warns about. `backend_signal.py` ships the naming/provenance rule as a
  **standalone** primitive (`BackendProbability` is a complete record on
  its own, embeddable in a future record without one existing yet).
- **J14's contract assumed a `dottie_loop/decision.py` "research stage 7"**
  wired into `compose_bundle` and `research.STAGES_LANDED`. Since no
  decision module was built (previous bullet), this PR does not claim a
  new numbered research stage or touch `research.py`, `STAGES_LANDED`, or
  `compose_bundle` — that pipeline is specifically the six-stage
  reward-composition sequence, and neither new module is part of it. What
  *did* survive from J14 — land through every registry surface, with an
  "establishes / does not establish" table and a "claims recorded, not
  adopted" list — is exactly what this document does.
- **C1's contract's `ExperimentManifest` used a `quality.verifier_record_sha256`
  instead of a free-text method,** an `adaptive_state` block, a
  `ran_marker`, and touched `factory/mlops.py`, `factory/train_queue.json`,
  and `reward.py` (a `gate_manifest` job kind, a `RewardInputs
  .latency_baseline_ms` field, `mlops.run()` recording `dirty`/
  `report_sha256`). This PR's `manifest.py` keeps the simpler
  `quality_method: str` + `quality_passed: bool` shape (closer to what
  colibri itself actually uses) and does not touch any file outside
  `packages/dottie-loop`. **SPECED-DEFERRED**, reversal trigger: a real
  Forge runner is registered (`docs/project_dag.json` node
  `forge-runner-register`) and produces comparative timing data worth
  gating a promotion on.
- **C3's contract added `opt_lane.run_calibrated_pair`, a `stats.py` with
  Wilson intervals, and a `baseline_provenance` freshness window on speed
  credit.** This PR ships the core of C3 that lives entirely inside
  `manifest.py` (`run_order`, `order_kind`, `pair_wins`) and defers the
  `opt_lane`/`reward.py` integration and the Wilson-interval helper (which
  the colibri research itself found no justified sample-size threshold
  for — "colibri never found a sufficient n"). **SPECED-DEFERRED**, same
  reversal trigger as above.
- **Median and changed-variables were made stricter than colibri's own
  practice**, not looser: colibri's validator accepts a *claimed* median
  and changed-variable list and cross-checks them; this PR's records
  simply have no field for a claim to disagree with the data in the first
  place. This removes a whole class of "claimed vs. derived mismatch"
  bug colibri's own validator exists to catch, at the cost of not
  supporting a workflow where a caller states its result before
  submitting evidence.

## Establishes / does not establish

| | |
|---|---|
| **Establishes** | Jev's own materials and independent reproductions do not show its confidence number to be a calibrated, error-flagging statistic — the specific, single highest-risk thing an integration could have imported as truth. |
| **Establishes** | colibri's own CI-enforced validator recomputes the same numbers it prints as a claim, and colibri's own experiment logs document that unpaired, non-interleaved timing comparisons produced wrong-signed conclusions on real hardware. |
| **Establishes** | Two small, tested, stdlib-only, fail-closed record types now exist in `packages/dottie-loop` for (a) holding an external probability without letting it alias an existing `confidence` meaning, and (b) filing a two-arm timing/quality comparison whose headline numbers a reader can re-derive. |
| Does **not** establish | That Dottie should call, host, or depend on either project. Neither is installed; `backend_signal.py` and `manifest.py` have no network access and no model in their import graph. |
| Does **not** establish | Any confidence/probability threshold (0.5, 0.6, 0.8, 0.85, 0.9 — every one surveyed across TypeSafe's own docs, the community integrations, and this codebase's existing code) as justified. No surveyed source supplies one; none is added here. |
| Does **not** establish | That colibri's own manifest schema is adopted as-is — its soft spots (string-only `quality.method` accepted without a linked record, shape-only `sha256` never recomputed, `quality.passed` required `True` on *both* arms making a real regression unfilable) were identified and deliberately not ported; see "Fork taken". |
| Does **not** establish | That this PR has measured anything about Dottie's own benchmarks, routing, or agents. It adds record *types* for future evidence to be filed against; it files none itself. |

exists); it needed at least two of three not to refute it, and got fewer.
"Declined before verification" means the distillation pass itself judged
the idea unfit for this codebase before a contract was even drafted.

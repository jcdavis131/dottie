# arxiviq.com — Ava MLOps platform architecture

**Solo personal project, no connection to employer, built with public/free-tier only**

## Tech stack & rationale

**Static-first, zero-backend.** Vanilla HTML/CSS/JS deployed on Vercel (project `arxiviq`).
No framework, no build step, no server — because every capability the platform needs is
satisfiable from *published artifacts*, and the ecosystem's binding constraints (free-tier
only; models run on a single consumer GPU at home, not in a cloud function) make a hosted
inference backend impossible and a hosted database unnecessary.

```
 GitHub releases (scout-rtx: results.jsonl)  ──┐   fetched client-side, polled 60s
 GitHub raw (factory: STATUS.json)          ──┤──►  arxiviq SPA (4 views)
 baked snapshot (generate_data.py)          ──┘   fallback + provenance badge
```

- **Data plane**: browser fetches GitHub releases API + raw contents (both CORS-enabled).
  When unreachable (private repo, offline), the site falls back to `site/data/*.json`
  baked at deploy time by `generate_data.py` — and the header badge switches from
  `● live · GitHub` to `◆ snapshot · baked <date>` so provenance is always visible.
- **Honesty invariants** (same anti-mock culture as the repos): mock-mode eval results are
  labeled "pipeline check, not model capability"; the snapshot carries `generated_at`;
  the console renders published numbers, it never computes fake ones.

## The four capabilities

1. **Training telemetry** — stat tiles (pipeline phase, trainer steps, weekly-training
   status chip, RTX experiment count) + `val_bpb` line chart from scout-rtx's auto-published
   release assets, polled every 60s. Real-time within the granularity the ecosystem
   actually publishes (scout-rtx pushes a release every 5 experiments).
2. **Checkpoint harness** — per-branch (base/code/math/chat) canonical J-test results with
   pass/fail chips + the exact `python -m harness run` command to reproduce. Dynamic
   evaluation runs on the training box (that's where the checkpoint and GPU live);
   the console is the results surface. This boundary is deliberate, not a gap.
3. **Evaluation dashboard** — frontier rubric overall-by-domain bar chart with per-rubric
   drill-down table (judge, mode, weights all surfaced).
4. **Model cards** — generated by `generate_data.py` from `configs/*.yaml` + scale-ladder
   state + eval artifacts: architecture, curriculum phase strip (token-proportional),
   provenance statement, constraints (incl. base1b VRAM risk), eval methodology.

## Design system

dataviz reference palette (validated via `validate_palette.js`, light + dark surfaces);
single categorical hue for single-series charts; status colors only as icon+label chips;
2px lines / 4px rounded bar ends / hairline grids; tabular numerals in tables; theme
toggle stamps `data-theme` (beats OS preference both ways); tooltips on all marks.

## Deploy / refresh

```bash
python arxiviq/generate_data.py            # re-bake model cards + snapshot from sibling repos
# deploy site/ to Vercel project "arxiviq" (production), then attach arxiviq.com
# in Vercel dashboard → Project → Settings → Domains (one-time)
```

## Deliberately out of scope

- **In-browser checkpoint execution** — a 171M-param torch checkpoint doesn't run in a
  static page or a Vercel function; pretending otherwise would fabricate results.
- **Write operations** (queueing evals from the web) — would require authenticated
  backend + policy checks; the `scout rtx queue add` CLI is the writing interface.

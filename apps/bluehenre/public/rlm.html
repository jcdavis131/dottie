ONE TOOL: A PERSISTENT IPYTHON KERNEL
The model gets exactly one tool — a persistent in-process IPython kernel whose namespace survives across calls. File edits, shell, messaging, compaction and sub-agents are ordinary Python functions inside that namespace; the model calls them in code, the kernel executes. The namespace is the only state the model manipulates directly.
SUB-AGENTS AS FUNCTION CALLS
rlm(prompt) spawns a child session — own kernel, own history — and returns at admission: {"id": …, "state": "admitted"}. It never blocks on the child's answer; the child runs its own loop and its final answer arrives later as a message in the parent's inbox(). Messaging is scoped to parent, siblings and direct children — anything else raises ScopeError.
H = (ρ, G, K, M)
The harness state: ρ the immutable base prompt (hash-pinned — refinement is rejected if it targets ρ); G sub-agent defaults; K skills; M memory. The effective prompt is rebuilt as ρ + skill listing + memory digest — never mutated in place.
REFINEMENT LEDGER + ROLLBACK
Every change to G/K/M is the smallest relevant edit, appended to an append-only ledger with its trigger and (later) its outcome. rollback(id) reverses an edit and is idempotent. The ledger card above is that file, verbatim.
THE LOOP
Fenced python blocks in the model's reply execute in the kernel, in order; results feed the next completion. A reply with no code block is the answer. Hitting the step limit is recorded honestly in the trajectory — never dressed up as an answer.

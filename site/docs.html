Run Dottie locally.

One file, zero dependencies, five minutes. Dottie Local is the job queue and worker CLI — the beating heart of the harness.

1 · Install

Clone the repo and run the installer. It builds a single dottie.pyz (8KB, stdlib only) and links it as dottie on your PATH:

git clone https://github.com/jcdavis131/dottie.git
cd dottie
bash scripts/install-local.sh

Add the queue location to your shell profile so it follows you everywhere:

export DOTTIE_JOBS_DIR="$HOME/.dottie/jobs"

2 · Submit your first job

dottie submit --goal "Summarize the open PRs on jcdavis131/dottie" --surface
dottie list --state pending

--surface means: report the result back when it's done. Without it, the result just lands in the queue, quietly.

3 · The loop

  1. Submit — the job spec lands in jobs/pending/.
  2. Claim — the worker atomically moves it to jobs/claimed/. One job at a time, no races.
  3. Work — the job is done with real tools. Read-only by default; anything destructive needs your explicit word.
  4. Record — dottie done writes the result; dottie log appends a 7-field timeline entry. Real traces, never theater.
  5. Surface — surfaced or failed jobs report back. Everything else stays silent.

Commands

CommandWhat it does
submitFile a job: --goal, --context, --repo, --surface
listJobs by state: --state pending|claimed|done|failed
showFull spec + result for one job
statusQueue counts as JSON
claimAtomically claim a pending job
done / failRecord the outcome, honestly
logAppend a timeline entry (node/agent/attempt/latency/tokens/status/error)

The rules

Dottie never bypasses your approval. Merges, releases, deploys, sends, and deletes need your explicit word — in the job spec and under the normal approval rules. Agent approval never counts. If a job can't be done, she fails it with the honest reason instead of inventing a result.
